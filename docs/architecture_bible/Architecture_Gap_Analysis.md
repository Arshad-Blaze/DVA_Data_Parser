# Architecture Gap Analysis

Comparison of the actual implementation against the intended architecture, with every
issue ranked Critical / High / Medium / Low.

Ranking scale:
- **Critical** — breaks the declared architecture or correctness; must be fixed before
  production.
- **High** — significant deviation or real risk; should be fixed.
- **Medium** — duplication, dead code, or inconsistency; nice-to-fix.
- **Low** — cosmetic/vestigial.

## Architecture-Compliance Answers (from the readiness report)

1. **Layer violations** — UI→ParserFactory (H2), Validation→Reports (H5), Reports→
   Aggregation (H6), Config→Detection (H1), Parser→join (H11/M11), flush→Streamlit (L-ish).
2. **UI performing backend work** — yes (H2, column validation, direct file reads).
3. **Backend depending on UI** — only `workflow/flush.py` imports Streamlit (guarded);
   otherwise no.
4. **Duplicate logic** — M12, M3, M4, L4 (mapping UIs, detection, aggregators, stage
   builders, store-list loading, ParseOptions building).
5. **Repeated detection** — H1 + M9.
6. **Repeated parsing** — H6 (file-review fallback).
7. **Multiple workflows** — Onboarding vs Existing are two full implementations sharing
   the same spine; overlap in orchestration is intentional but duplicated parameter
   threading.
8. **God classes** — `ProcessingContext` (many roles but acceptable state holder);
   `ui/helpers.py` (1070-line grab-bag); `detection.py` (1504-line heuristic engine);
   `_parsers.py` (759-line engine).
9. **Circular dependencies** — none hard; lazy imports used to break the
   workflow↔operations↔canonical graph.
10. **Missing abstractions** — a workflow state machine (C1), a single parse service
    (H2), a report-generation service detached from validation (H5).
11. **Incomplete implementations** — Excel (H12), Sales+Product (H11), tolerance /
    dup-UPC / missing-UPC (H3), OutputMode variants (M13), TEST-side KPIs (H10).
